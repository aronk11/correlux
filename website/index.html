✖ down → ⚠ degraded → ? unknown → ✓ healthy

Applications sort worst first, never alphabetically — an application Correlux cannot vouch for outranks one it knows is fine. A cluster that does not answer is unreachable, on its own row, with the reason stated. It is never folded into a healthy count, and it never reads as zero problems.

Application-first navigation

Kubernetes has no application object. Correlux infers one anyway.

Every workload is walked up its owner references to the controller that is not itself owned, so a ReplicaSet resolves to its Deployment and a Job to its CronJob. Workloads that share an app.kubernetes.io/instance label, or fall back to app.kubernetes.io/name, app or k8s-app, join the same release. Services join by label or by a selector that actually matches the pods found; ingresses join by label, or through the service they route to.

The inference is heuristic, and Correlux says so: an object that matches nothing is left out of every application rather than invented into one, and stays fully visible in the resource browser.

Why / evidence

A deterministic explanation, built from the cluster's own evidence.

Press Ctrl+W. Thirteen rules read pod conditions, container states, restart counts, events, endpoints, node conditions and volume claims — no model runs anywhere near it.

Fact

What the API server actually stated: replica counts, exit codes, event messages, endpoint lists.

Inference

The one reading the facts support — here, that repeated OOM kills explain zero available replicas.

Unknown

What Kubernetes cannot say — why memory usage grew — is left unset. Correlux lowers its confidence rather than inventing a cause.

Multi-cluster

Several clusters, one bounded, cancellable pass.

Every cluster in the fleet is read concurrently, within a client timeout, and every remote value carries an explicit lifecycle: loading is never confused with empty. Switching context cancels whatever was still in flight rather than letting a stale answer land late.

A cluster that cannot be reached is a member whose state says so — never a silent gap that reads as health. The fleet overview is read-only: opening it never mutates anything, and acting on a row leaves the fleet for the one cluster it belongs to, so a change always lands on exactly the cluster you meant.

  • bounded Every fleet read runs under a client timeout; nothing waits forever on one slow cluster.
  • cancellable Switching cluster or namespace cancels in-flight requests instead of racing them.
  • fault-tolerant One unreachable cluster narrows its own row. The rest of the fleet still answers.
  • no accidents The overview is read-only; a mutation always happens inside one specific cluster, never across the fleet.
Installation

One binary. No runtime to manage.

01

Homebrew (macOS)

The primary install path. The tap ships a cask, so Linux takes one of the two below.

brew install aronk11/tap/correlux
02

Release binaries

Static binaries for macOS, Linux and Windows — nothing else to install.

Download from github.com/aronk11/correlux/releases
03

Go toolchain

If you already have Go installed.

go install github.com/aronk11/correlux/cmd/correlux@latest
04

Run it

Starts in your current kubeconfig context. No flags required.

correlux

Start somewhere specific, or check why it doesn't work here:

correlux --context prod-eu
correlux doctor
